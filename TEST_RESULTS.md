# Purrbi test results

Mocked tests and live tests are kept separate. "Mocked" = synthetic inputs labelled `TEST FIXTURE`; "emulator" = Firebase Local Emulator Suite (no production data); "live" = real public services or the deployed backend.

## Categories (kept separate)
1. **Mocked** — unit tests with labelled TEST FIXTURE inputs; network stubbed.
2. **Emulator** — Firebase Local Emulator Suite; security rules and the real job code, sources mocked.
3. **Emulator + real network** — the real function code on emulators with real source adapters (GitHub Actions has open internet; this session does not).
4. **Live public providers** — real Open Pet Food Facts / Open Food Facts / openFDA / citation pages from GitHub Actions; no Purrbi backend involved.
5. **Live deployed backend** — the deployed Firebase project (`purrbi-49c21`), driven by client requests only (`live-e2e`: Auth REST sign-up, Firestore/Storage REST with the user's token, so the deployed rules apply).
5b. **Live app in a browser** — the real app (FlutterFlow export, release web build) in Chromium at phone size against the deployed backend, driven through its accessibility tree. Sandbox workarounds, nothing else changed: the Firebase JS SDK is served from the official npm package (this sandbox blocks `www.gstatic.com`), and Chromium's GET of an uploaded photo is re-sent through Playwright (this sandbox's proxy answers Chromium's Storage GET with 400; uploads go through the browser). Not a phone: camera, gestures and Android behaviour are not covered.
6. **Android build** — `android-apk` workflow on GitHub, with `google-services.json` from the repository secret `FIREBASE_GOOGLE_SERVICES_JSON` (checked to be for `purrbi-49c21` and this app). Built, not yet installed on a device.
7. **Physical device** — *pending; not possible in this environment.*

Notes:
- `backend/tools/loopback-no-proxy.cjs` is a sandbox-only test preload (firebase-tools ignores `NO_PROXY`); not used on GitHub.
- `RETRY_TEST_BARCODES` (deploy-config.json, development only) makes the first attempt of the listed barcode fail like a source outage, so the retry path can be shown on the deployed backend; retries are never affected.
- Trace ids are the `traceId` of each scan document (also in the function logs); HTTP outcomes per call are in each scan's `sourceChecks`, and why AI-found information was or was not used is in `diagnosticNotes`.
- GitHub reports are read through check-run annotations because artifact downloads are blocked in this session.
