# Purrbi API & data contract

Version: 2026-10-30 (assessment `assessment-3.0.0`) · backend `purrbi-functions` (Firebase codebase `purrbi`, Node 22, region `us-central1`).
Status column: **verified** = exercised by tests in this repo · **emulator** = verified on the Firebase emulator only · **pending live** = written against published docs, not yet checked against the live service (this session's network policy blocks those hosts; the CI job `live-contract` checks them).

## 1. Client ↔ backend protocol

There are **no HTTP or callable endpoints**. The app talks to the backend only through Firestore documents; Firestore rules restrict every path to its owner. Triggers run server-side with the Admin SDK.

| Step | Client writes | Backend trigger | Backend writes | Status |
|---|---|---|---|---|
| Start scan | `users/{uid}/scans/{scanId}` = `{barcode: String (digits, leading zeros kept), petId?: String, source?: "camera"\|"manual", status: "queued", createdAt: serverTimestamp, clientVersion?: String}` | `processScanJob` (onDocumentCreated) | status/progress updates, then result fields (§3) | emulator |
| Add label photo | upload image to Storage `users/{uid}/uploads/...` (FlutterFlow Upload), then `users/{uid}/photos/{photoId}` = `{scanId, purpose: "front"\|"ingredients"\|"nutrition"\|"label", imageUrl: String (that file's download URL), status: "uploaded", createdAt: serverTimestamp}` (scan `needs_photos`, `complete` or `out_of_scope`) | `processScanPhoto` | photo `{status: processing→processed\|unreadable\|different_product\|failed\|rejected, stage: extracted\|corroborated\|verified\|disputed, stageNote, statusMessage, panels[], fieldsFound[], uncertainFields[], processedAt}`; scan re-assessed | emulator |
| Retry after failure | scan `{retryRequested: true}` (when `status == "failed"` and `errorRetryable == true`, or when a working status has had no update for 6 minutes: the job stopped without a result) | `onScanRequestUpdated` | re-runs the job (a stuck scan is not charged again) | emulator |
| Continue without photos | scan `{skipPhotos: true}` (only when `status == "needs_photos"`) | `onScanRequestUpdated` | `status: "complete"` with the findings so far; `photoRequests` are kept, so photos can still be added later (the result is re-assessed when one is read) | emulator |
| Personal fit for another pet / after profile edit | scan `{refreshPersonalRequested: true, petId}` (status `complete` or `needs_photos`) | `onScanRequestUpdated` | personal fields recomputed from the saved evidence (no source is read again); general score unchanged unless evidence changed; the result keeps its status | emulator |
| Re-check a saved result made under older rules | the app sends the same `{refreshPersonalRequested: true, petId}` when it opens a saved result whose `assessmentVersion` is older than the current one (`assessment-3.0.0`; a missing or unreadable version counts as older) and no refresh is pending; status `complete`, `needs_photos` or `out_of_scope` | `onScanRequestUpdated` | the whole assessment is re-run under the current rules: it may re-read the product's sources where its saved record is out of date (the usual per-product limits and caches) and check explanations under the current rules; the photos the current rules need are asked for again unless the owner chose "Continue without photos"; the verdict is rewritten and `evidenceNotes` says which rules the earlier result used. Charged to the owner's daily `refreshes` quota (40): past it, the saved evidence is used and the result keeps its old version, so the re-check happens on a later opening. Saved research from an earlier method is kept until research under the current method has returned; when it could not run (provider error, quota, switch off, time limit), the result keeps its old version (`assessmentVersion` is not stamped current) and is re-checked later. A result whose version is newer than the backend's (a later release, before a rollback) is left as it is, and a run whose inputs are older than the saved result never overwrites it | emulator |
| Save / unsave | scan `{favorite: Boolean}` | — | — | emulator |
| Delete a result | delete scan document | `onScanDeleted` | deletes its photos, their files and the label text read from them | code reviewed |
| Delete account | Firebase Auth delete | `cleanupDeletedUser` (v1 auth onDelete) | recursive delete of `users/{uid}`, Storage `users/{uid}/`, usage counters | code reviewed |

Authentication: Firebase Auth ID token on every Firestore request (SDK-managed). Unauthenticated clients can read nothing.

### Scan status values
`queued` → `identifying` (10) → [`researching` (35)] → [`checking_alerts` (60)] → `assessing` (85) → `complete` | `needs_photos` | `out_of_scope`; `processing_photo` (70) while a photo is read; `failed` with an error code.

### Error codes (`errorCode`, `errorRetryable`, `errorMessage`)
| Code | Meaning | Retryable |
|---|---|---|
| `invalid_barcode` | not 8/12/13/14 digits or wrong GS1 check digit | no |
| `quota_exceeded` | per-user daily scan limit (40) reached | no (resets 00:00 UTC) |
| `source_unavailable` | product database timed out / unreachable and nothing cached | yes |
| `analysis_failed` | unexpected error during assessment | yes |
| `save_failed` | result could not be written | yes |
"Product not found" is **not** an error: it is `status: needs_photos`, `productFound: false`, `missingInfo` includes `front`.

Every scan has a `traceId` (12 hex chars) used in all backend logs and evidence records for that run.

HTTP 4xx) 6 hours; no explanation, no citation, or a citation off the allowed sites 1 day; anything not verified is asked for again when `version` changes |

| `knowledgeAudit/{key}__{oldVersion}` | backend | nobody (rules deny every client read and write) | one record per withdrawn explanation: `term`, `kind`, `species`, `oldVersion`, `oldStatus`, `oldSummary`, `oldSourceTitle`, `oldSourceUrl`, `oldQuote`, `oldModel`, `oldCheckedAt`, `withdrawnAt`, `supersededBy`, `reasons[]` (why it would not pass now) |

Barcode keys: `gtin14` = digits left-padded to 14 (UPC-A `036000291452` and EAN-13 `0036000291452` are the same product). `barcode` keeps the digits exactly as scanned.

### Open Food Facts / Open Beauty Facts / Open Products Facts — scope only (live-verified)
Same API; queried only when the pet database has no record. Verified: UPC `036000291452` → Open Pet Food Facts 404 → Open Food Facts 200 "Alaska Peanut Butter - Creamy" → out of scope (human food). The Open Food Facts *search* endpoint sometimes returns HTTP 503; product lookups were unaffected.

### openFDA food enforcement — recalls (live-verified)
`GET https://api.fda.gov/food/enforcement.json?search=(recalling_firm:"{brand}"+product_description:"{brand}")&limit=100&sort=report_date:desc`
HTTP 200; the pet-food query (`"dog food" "cat food" "pet food"`) returns only a handful of records (3 on 2026-10-28), so coverage of animal-food recalls in this endpoint is thin. The result text always says so: "updated weekly and doesn't include every FDA animal-product notice". Match rules: barcode digits in `product_description`/`code_info` → `exact_barcode`; ≥60 % name overlap → `brand_and_product`; else `brand_only`; active = `Ongoing`/`Pending`.

### OpenAI — label reading, research and explanations (pending deploy)
- **Label reading** (owner photos and database label images): `POST /v1/chat/completions`, model `OPENAI_VISION_MODEL` (default `gpt-4o-mini`; dev `gpt-4.1-mini,gpt-5-mini`), strict schema `pet_label_transcription`: each visible panel transcribed verbatim with its legibility and `[?]` for anything uncertain. Purrbi takes the values from the transcription with its own rules (`domain/analysisText.ts` for the analysis) and keeps only what two independent readings agree on; guarantees are range-checked. A photo counts as another product only when both readings show the same other valid barcode (a photo without a barcode is accepted). Reader `label-extract-2.3.0`; readings by 2.2.0 stay in use; readings by 2.1.0 keep only their plain analysis rows (one nutrient named, no other number, in %, within food-level bounds, no second value), their ingredient list is cut again where an analysis starts, and a reading disputed only because of a row now set aside is staged again.
- **Barcode lookup hint** (`BARCODE_LOOKUP_ENABLED`, trial): `GET https://api.upcitemdb.com/prod/trial/lookup?upc={code}` (no key; 100 requests/day). Only the title and brand are used, and only as search words for the research step below: nothing from it is shown or used as a product fact.
- **Manufacturer/web research** (`research-2.0.0`; results of 1.7.0 are kept until a 2.0.0 run has returned, then replaced): each fetched page is tied to the product on its own — by a barcode in its text or markup (one distinct barcode, or a Shopify variant whose barcode matches, tied to the URL by `?variant=` when the product has several), by the same recipe (at least 5 ingredients compared, 80% matching, the brand on the page), as one of a family of sizes or flavours (the barcode is one of several on the page), or by a trusted name in the page's heading with the species. Only a barcode- or recipe-tied page may supply the analysis, calories, package size or the ingredient list; a family or name page supplies only the species (as a superset), an intermittent-feeding statement or a single-ingredient list. Downloads are bounded (page and PDF size caps; a PDF with scripts or embedded files is refused) and the whole research step stops after 200 s, keeping what was verified. If the AI budget runs out at the manufacturer follow-up, what the first page verified is kept. reads the cited page's text, image alt text, markup barcodes (`data-upc`, `ps-sku`, JSON-LD `gtin`; at most 3 distinct), a Shopify product's `.js` record, and nutrition documents (PDF) the page links to; after a retailer page it looks for the manufacturer's page for the fields still missing. A page that names the product but shows no barcode or same recipe may supply only the species, the feeding statement and a single-ingredient list — never an analysis, calories or a similarly named variant's ingredients. A provider error is reported as such, never as "product unknown". Earlier method (`research-1.7.0`): `POST /v1/responses` with `web_search`, strict schema `pet_product_research`; a field is kept only if Purrbi finds it again on the cited page it fetches itself (barcode, or brand + name, on the page), a value only where the page prints it as a number of its own. The analysis printed on the page is also read by Purrbi itself, with the label rules, from the fetched page that is itself shown to be this product (barcode first, else brand and name); it is used when it gives more of the analysis than the model's answer, or when the answer disagrees with it. On by default; attempted at most once per product per 30 days, and once more after a new research method while something is still missing (results of `research-1.6.0` stay in use).
- **Cited explanations** (`explain-2.0.0`): claim by claim. Each claim names the exact ingredient form, its passage, the species or use the source is about, the dose context, the evidence kind and the dates; Purrbi checks each one itself (the passage is on the cited page and names the same form; the source is about cats, dogs or pets for a safety, dose or benefit claim — not swine or people; a product-naming rule is not a claim about an ingredient; a palatability or processing passage does not support a nutrition or health claim), then a second model call judges whether the passage supports the claim as worded (`judgeModel`). Claims that fail are dropped and recorded in `rejected`; the rest are shown with their sources. A claim is cached under the term's key (`knowledge/{species}_{kind}_{term}`), so the same ingredient in another product reuses it. Up to 80 of a scan's terms are looked up in the cache and up to 24 new ones explained per assessment, 4 per call (the rest follow on later scans). Explanations and the verdict that a job reaches after 100 s are handed to a run of their own (`explanationsQueued`), which adds them from the saved evidence. Earlier explanations (`explain-1.x`) are withdrawn with an audit record (`knowledgeAudit`): when a scan asks for the term again, and by a sweep of up to 10 earlier entries per assessment, so a term no scan asks for any more is withdrawn too (one never shown is removed). The web search is limited to 18 authoritative sites (FDA, eCFR, AAFCO, FEDIAF, EFSA, Merck/MSD Veterinary Manual, VCA, VIN Veterinary Partner, ASPCA, Pet Poison Helpline, WSAVA, AVMA, Cornell, Tufts Petfoodology, NCBI, NIH ODS, Today's Veterinary Practice); all of a scan's new terms (up to 20) in parallel calls of 8 terms; kept only if the verbatim quote is on the cited web page (the model is asked for web pages; a cited PDF, Office document or other file is recorded as one Purrbi cannot check, not as a missing quote). Never changes a score.
