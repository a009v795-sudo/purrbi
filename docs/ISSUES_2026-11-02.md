## Firestore indexes (FF-E1)

**Queries.** The app's queries come from the generated code:
- `photos where scanId == … orderBy createdAt`;
- `pets where onboardingComplete == true orderBy createdAt`;
- `pets where onboardingComplete == false orderBy updatedAt desc limit 1`;
- `scans orderBy createdAt desc limit 100`;
- `scans where favorite == true orderBy createdAt desc limit 100`.

The backend's queries are single-field.

**One source of truth.** That is `backend/firestore.indexes.json`, with 5 composite indexes. The CI step `backend/tools/check-indexes.mjs` derives the needed indexes from `app/lib` and fails when one is missing; today: "All 4 app queries that need a composite index have one." FlutterFlow's generated set is exactly those 4.

**Deployed.** The deploy workflow deploys indexes from the repository file only. Its verification step read them back from the Firestore API for deploy run 41408940343: all 5 `READY` in `purrbi-49c21 (default)`.

**Live, as an ordinary test user.** The app's queries returned HTTP 200 (Q1–Q7). A control query that needs an index that does not exist returned `FAILED_PRECONDITION`, which shows a missing index would be caught. The emulator does not enforce composite indexes, so these checks were live.

**No deploy was needed.** A broad deploy was not run, and FlutterFlow's generated security rules were not deployed.

**The editor's red badge stays.** FlutterFlow tracks only deploys made from its own Settings page, which needs FlutterFlow's service account to have deploy rights on the Firebase project. That access is not granted (least privilege). The badge is FlutterFlow's record, not the project's state.

## Label reader 2.5.0 and the misread-digit rule (BE-1, BE-2)

- The adequacy statement is asked for as its own panel, transcribed whole, even when it runs into the calorie content.
- A formally worded statement printed over several lines is read as one sentence. "…established by the / AAFCO Cat Food Nutrient Profiles for maintenance." keeps its life stage.
- A front's separate lines are never joined into a statement.
- An owner's photo gets a **third reading**, by the model whose reading lacked it, when only one of the two readings gives the ingredient list or the adequacy statement, or they differ. What is kept is still read alike by two different models. A third reading that agrees with neither, or fails, changes nothing.
- Database label images keep two readings (the scan's time limit).
- A photo whose barcode is the scanned one, and whose only conflict is one analysis row one digit apart, is verified for the rest:
  - the saved analysis is kept;
  - the photo says so;
  - it is used for its owner only and never promoted.
- A larger difference, two rows, or another recipe still disputes the photo.
